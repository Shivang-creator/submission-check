# submission-check

**Lint a hackathon submission before you send it.**

```bash
python cli.py draft.md
```

No dependencies. No API key. No account. Standard library only — it runs offline.

---

## Why this exists

On **12 August 2026** I learned that **ProofPrint didn't place** at the Backblaze
Generative Media Hackathon. I read the three winning writeups next to my own that
evening. The gap wasn't engineering — it was four specific mistakes I could have caught
in ten minutes:

| What I did | What the winners did |
|---|---|
| Never stated a test count | Led with **"358 executable assertions"** and **"485 tests"** |
| Buried my best number (34×, 0/64 bits) at item 3 of a sub-list | **"9.3s vs 65.7s on job `j_47cdc2`, live — check it yourself"**, first line |
| Named my audience once, in *"What's next"* | Named the buyer in paragraph one |
| Wrote three SDK bugs under *"Challenges we ran into"* | Filed **3 PRs and an issue** with reproductions and failing tests — and led with it |

`submission-check` is those lessons as executable rules. Every rule in
[`RULES.md`](RULES.md) carries a **provenance** column naming the hackathon it was
learned in. Nothing here is hypothetical.

## The proof

The repo ships two real fixtures — a losing submission and a winning one:

```bash
python cli.py fixtures/proofprint.md    # my entry that lost. lights up.
python cli.py fixtures/firstframe.md    # the entry that won. nearly silent.
```

Same linter, two files, opposite verdicts.

## What a finding looks like

Every finding quotes the **exact span** that triggered it, gives **one imperative fix**,
and names the **loss it came from**. No finding is generated by a model, because a model
would make the evidence unverifiable — and unverifiable findings are the problem this
tool exists to fix.

## The one guarantee, enforced not promised

Every finding quotes a **verbatim span** of your draft. `run_checks()` enforces this
mechanically — a rule returning evidence that isn't an exact substring of the input
raises `EvidenceError` and the run fails. The tool cannot invent a quote to justify a
finding, even by accident.

Given that its job is telling you your evidence is weak, it holds itself to the standard
it enforces.

## The ten checks

1. No test count stated
2. Headline number buried past the first quarter of the document
3. Audience deferred to *"What's next"*
4. SDK bugs written as complaints rather than filed as contributions
5. Opens with a regulation instead of a person
6. No visible failure — perfect surfaces read as untested
7. A guarantee asserted but never attacked
8. Required links missing (repo, live URL, demo video)
9. Stated rules not addressed
10. *"Works with no API key"* not said up front

Full provenance for each in [`RULES.md`](RULES.md).

## Built with Agent Orchestrator

Built during The Orchestra hackathon (12–13 Aug 2026) using [AO](https://aoagents.dev/)
as the coding workspace — worker sessions in isolated git worktrees, tracked on one
Kanban board.

Four earlier sessions are terminated on that board and I've left them visible. They died
on environment friction: a missing `tmux`, a folder-trust prompt, and permission dialogs
that stalled every agent until I committed a `.claude/settings.json` the worktrees could
inherit. About forty minutes of a two-and-a-half-hour window.

Rule 6 of this linter is *"no visible failure."* It would be a poor advertisement to hide
my own.

## Honest limits

It lints **structure and placement, not truth.** It can tell you your headline number sits
68% of the way through the document. It cannot tell you the number is wrong. It flags a
missing test count; it cannot verify the count you write.

It's a checklist that learned from losing. It is not a judge.
